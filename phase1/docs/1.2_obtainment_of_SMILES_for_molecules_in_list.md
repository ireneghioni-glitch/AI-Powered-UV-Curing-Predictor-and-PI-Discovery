# Phase 1 - Step 2: Fetch Molecules Development Log

## From Specification to Production Code

### Document Purpose

This document chronicles the complete development journey of the `fetch_molecules.py` script, from its initial conception through multiple iterations to the final production version. It explains the reasoning, the obstacles encountered, and the iterative refinements that shaped the current solution. This log serves as both documentation and a learning resource for understanding how to adapt specifications to real-world data constraints.

---

## 1. The Original Vision (What the Spec Said)

The MVP Technical Specification ([curing-prediction-pipeline-mvp-v3-en.md](./curing-prediction-pipeline-mvp-v3-en.md)) defines Phase 1 as:

> **"SMILES Ingestion**: Load known molecules (e.g., Benzophenone: `O=C(c1ccccc1)c2ccccc2`) using the **RDKit** cheminformatics library."

This implies a straightforward workflow:

[KNOWN SMILES] 
    → RDKit (MolFromSmiles) 
    → RDKit (Draw.MolToImage) 
    → OpenCV (grayscale) 
    → Data Augmentation 
    → Save

The specification assumes that the developer already possesses a curated list of SMILES strings for all target molecules. In an ideal setting with pre-existing data, this is the correct and most efficient approach.

---

## 2. The Real-World Constraint (What We Actually Had)

In practice, we did not have a pre-existing list of SMILES strings. We only had:

| Data Type | Examples |
|-----------|----------|
| Molecule names (commercial trade names) | "TPO", "Irgacure 184", "Benzophenone" |
| IUPAC names as fallback | "Diphenyl(2,4,6-trimethylbenzoyl)phosphine oxide" |
| Chemical roles | Type I, Type II, co-initiator, monomer |

Therefore, the first mandatory step was to obtain the SMILES strings from the molecule names. The workflow had to be extended:

[MOLECULE NAMES] 
    → [SMILES RETRIEVAL] 
    → RDKit 
    → Image Generation 
    → ...

The retrieval step became a critical sub-phase that the original specification did not explicitly cover.

---

## 3. Initial Approach: pubchempy (The "Natural" Choice)

The most common and documented way to fetch chemical data from PubChem in Python is the `pubchempy` library. It provides a high-level, Pythonic wrapper around the PubChem REST API.

A typical call:

    import pubchempy as pcp
    compounds = pcp.get_compounds("Benzophenone", "name")
    smiles = compounds[0].isomeric_smiles

**Why we chose this first:**

- Well-documented and widely used
- Minimal code to write – handles HTTP requests internally
- Automatically manages rate limits and error conditions
- Returns rich Python objects with properties like `isomeric_smiles`, `canonical_smiles`, `molecular_weight`, `xlogp`, etc.

For a quick MVP, this was the obvious and safest starting point.

---

## 4. Problem Discovery: pubchempy's Limitations

During the first execution, we observed a critical failure:

- `pubchempy` would successfully return a compound object (with a valid CID) for many names, but the `isomeric_smiles` attribute was often `None`.
- For example, "Irgacure 651" returned CID 90571, but `smiles` was `None`. The correct SMILES belonged to CID 638686.
- The root cause: PubChem stores multiple records per compound (e.g., salts, mixtures, alternative tautomers). The `name` search often returns the wrong record – one that does not have SMILES populated.
- This happened for most Type I photoinitiators, many Type II, and even common co-initiators like "Triethylamine".

**Example of the problem:**

    # Expected: COC(OC)(C1=CC=CC=C1)C(=O)C2=CC=CC=C2
    # Got: None
    compounds = pcp.get_compounds("Irgacure 651", "name")
    print(compounds[0].cid)      # 90571 (wrong)
    print(compounds[0].isomeric_smiles)  # None

This was a fundamental mismatch between the library's behavior and our requirement. We needed the canonical SMILES of the active principle, not whatever record PubChem happened to return first.

---

## 5. Second Iteration: Adding Cache and Fallback Logic

To mitigate the problem, we enhanced `get_smiles_robust()` with:

- A local CSV cache (`smiles_cache.csv`) to avoid repeated API calls
- A two-stage fallback:
    1. Try each `primary_names` (trade names) in sequence
    2. If all fail, try `alt_name` (IUPAC name)
- Rate limiting (`time.sleep(0.5)`) to respect PubChem's limits

**Initial cache function structure:**

    def get_smiles_robust(primary_names, alt_name=None):
        df = load_cache()
        
        # Check cache first
        for name in primary_names:
            if name in df["trade_name"].values:
                return df[df["trade_name"] == name]["smiles"].iloc[0]
        
        # Try primary names
        for primary in primary_names:
            compounds = pcp.get_compounds(primary, "name")
            if compounds and compounds[0].isomeric_smiles:
                smiles = compounds[0].isomeric_smiles
                save_to_cache(primary, smiles)
                return smiles
        
        # Fallback to alt_name
        if alt_name:
            # ... similar logic

This was a step forward, but it only addressed the search strategy, not the core issue: `pubchempy` was still returning compounds with `isomeric_smiles = None`.

## 6. Critical Bug: The "Break" Statement

A critical bug was discovered in the main execution loop:

    for idx, item in enumerate(molecules_config, 1):
        smiles, used_name = get_smiles_robust(...)
        if smiles is not None:
            found_smiles = smiles
            found_name = used_name
            break  # ← THIS WAS THE PROBLEM
        else:
            ...

**The issue:** The `break` statement caused the script to exit after the first successful molecule. This meant that only one molecule was processed, and all subsequent ones were skipped, resulting in a CSV with only one entry.

**Additional problem:** The cache DataFrame had inconsistent column ordering:

    # load_cache() returns: ["iupac_name", "trade_name", "smiles"]
    # save_cache() writes:   ["trade_name", "iupac_name", "smiles"]

This caused data to be saved in the wrong columns, corrupting the cache and leading to `NaN` values in the final CSV.

Both issues were fixed in subsequent iterations.

---

## 7. Realisation: pubchempy Is Not the Right Tool for This Job

After numerous debugging cycles, we had to accept a hard truth:

> `pubchempy` is an excellent library for many use cases (retrieving molecular weight, XLogP, formula, etc.), but it is **unreliable** for obtaining SMILES strings for arbitrary compound names.

**Why?**

1. PubChem's PUG REST API (which `pubchempy` wraps) returns the **first matching compound** for a name search
2. That compound may not have a SMILES string, or it may not be the isomer we need
3. The API does not provide a direct way to "get the canonical SMILES for this specific commercial name" without first knowing the correct CID

**At this point, we had two options:**

| Option | Description | Pros | Cons |
|--------|-------------|------|------|
| A | Continue "taming" `pubchempy` with increasingly complex fallback logic | No rewrite needed | May still fail for edge cases |
| B | Abandon the wrapper and call the PubChem REST API directly | Full control over requests and responses | More code to write |

**We chose Option B.**

---

The current version of `fetch_molecules.py` uses a hybrid strategy:

### Key Code Components

**Function to get SMILES from CID:**

    def get_smiles_from_cid(cid):
        url = f"https://pubchem.ncbi.nlm.nih.gov/rest/pug/compound/cid/{cid}/property/CanonicalSMILES/TXT"
        try:
            response = requests.get(url, timeout=10)
            if response.status_code == 200:
                smiles = response.text.strip()
                return smiles if smiles else None
        except Exception as e:
            print(f'    [API ERROR] {e}')
        return None

**Function to get CID from name:**

    def get_cid_from_name(name):
        url = f"https://pubchem.ncbi.nlm.nih.gov/rest/pug/compound/name/{name}/cids/TXT"
        try:
            response = requests.get(url, timeout=10)
            if response.status_code == 200:
                cids = response.text.strip().split()
                if cids:
                    return int(cids[0])
        except Exception as e:
            print(f'    [API ERROR] {e}')
        return None

**Robust SMILES retrieval with manual fallback:**

    def get_smiles_robust(primary_names, alt_name=None):
        # 1. Check manual dictionary
        for primary in primary_names:
            if primary in manual_smiles:
                return manual_smiles[primary], primary
        
        # 2. Try each primary name via REST API
        for primary in primary_names:
            cid = get_cid_from_name(primary)
            if cid:
                smiles = get_smiles_from_cid(cid)
                if smiles:
                    return smiles, primary
        
        # 3. Try alt_name (IUPAC)
        if alt_name:
            if alt_name in manual_smiles:
                return manual_smiles[alt_name], alt_name
            cid = get_cid_from_name(alt_name)
            if cid:
                smiles = get_smiles_from_cid(cid)
                if smiles:
                    return smiles, alt_name
        
        return None, None

## 10. Key Lessons Learned

### A. The Specification Is a Guide, Not a Rigid Script

The specification said "use RDKit for SMILES ingestion" – this assumes you already have SMILES. We had to adapt to the real-world constraint of starting from molecule names. This is a common situation in data science: the ideal workflow often requires an extra data acquisition step.

### B. Wrappers Are Convenient but Not Infallible

`pubchempy` is excellent for many tasks, but for retrieving SMILES strings reliably, direct REST API access is often more robust. The library's convenience comes at the cost of control and transparency. When dealing with critical data (like SMILES strings), it's worth understanding the underlying API.

### C. Fallback Strategies Are Essential

The manual dictionary of known SMILES strings was a critical safety net that guaranteed success for the most important molecules. A hybrid approach (API + manual fallback) combines the breadth of the API with the reliability of curated data.

### D. Always Validate Your Data

The final CSV was checked manually to ensure that the SMILES strings were correct and corresponded to the intended molecules. Automated validation (e.g., checking that `Chem.MolFromSmiles()` doesn't return `None`) is also essential.

### E. Simplicity Over Complexity

Removing the cache and using the REST API directly resulted in fewer bugs and easier maintenance. While caching is generally a good practice, it adds complexity that wasn't necessary for this MVP scale.

### F. Debugging Is Iterative

The journey from initial script to final production version involved:

1. Choosing the most obvious tool (`pubchempy`)
2. Identifying its limitations
3. Adding fallback logic
4. Discovering critical bugs
5. Switching to a more robust approach
6. Validating the results

Each iteration brought us closer to a working solution.

## 12. Next Steps

Now that we have a validated CSV of SMILES strings, we can proceed to the next phases of the pipeline exactly as described in the original specification:

### Phase 2: Computer Vision & Feature Extraction

    [SMILES from CSV] 
        → RDKit (MolFromSmiles) 
        → RDKit (Draw.MolToImage) 
        → OpenCV (grayscale, 224x224) 
        → Data Augmentation (rotations 90°, 180°, 270°) 
        → NumPy arrays ready for CNN input

    [Images] 
        → Pretrained CNN (MobileNetV2/ResNet50) 
        → Extract embeddings (penultimate layer) 
        → Train regressor on embeddings + target values

### Phase 4: Tabular Integration & XGBoost

    [Embeddings] + [Environmental features (Is_Aqueous, LogP, Dose, %PI)] 
        → Concatenate 
        → Train XGBoost Regressor 
        → Predict %Curing Conversion

    [Web App] 
        → React + Reflex state management 
        → User inputs SMILES and parameters 
        → Pipeline processes input 
        → Predicts curing conversion 
        → Saves to database

## 13. Conclusion

The journey from the initial `pubchempy`-based script to the final REST-API + manual-fallback version reflects a fundamental principle of software engineering:

> **"The specification tells you WHAT to do. The data tells you HOW to do it."**

The original specification was correct and clear: we need to ingest SMILES and convert them to images. But the specification could not predict that our source data (molecule names) required an extra transformation step. By identifying the gap and adapting our approach, we delivered a working, validated dataset that meets all the requirements of the project while being robust, maintainable, and ready for the subsequent phases.
